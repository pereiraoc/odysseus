# Career and Wallet apps for the Life hub: data sources (Brazil), product patterns, secure storage of sensitive documents

Scope: single user in Brazil, Odysseus web app on the laptop, reached from the phone through the NAS proxy with central login; NAS runs NixOS + Docker + Nextcloud + encrypted secrets. Research date: 2026-11-06. Labels used: **[official]** = government/vendor primary page; **[secondary]** = news/blog/law-firm/vendor-competitor; **[possibly outdated]** = page date older than ~12 months or unclear.

## Q1. Career data sources in Brazil: what each source holds, how to get it out, and in what format

### Takeaway
None of the Brazilian government sources has a citizen-facing API. Everything comes in as a manual download, usually a PDF, so Career has to be an "upload + parse + review" app, not a sync app. The richest structured sources are: LinkedIn's ZIP export (profile, positions, education, skills, certifications), the Meu INSS CNIS extract (every formal employment relationship plus monthly pay, PDF, free, only gov.br Bronze needed), the CTPS Digital (eSocial-based contracts, PDF export), the yearly informes de rendimentos plus the IRPF pre-filled return (income per payer per year), and the UFRGS Portal do Aluno transcript (electronically authenticated) plus the MEC Diploma Digital (signed XML).

### Cited Findings

**LinkedIn "Download your data"**
- Path: Me → Settings & Privacy → Data Privacy → "Download your data" → choose data → "Request archive". Selecting specific data types sends the email "within minutes". The larger download sends it "within 24 hours". The file stays downloadable for 72 hours. The page lists the categories "available within 10 minutes" (Profile, Positions, Education, Skills, Certifications, Invitations, Receipts…) and those "available within 48 hours" (Connections, Messages, Logins, Comments, Reactions, Shares, Search Queries, Inferences). Note that the page itself conflicts on 24 h vs 48 h. [official] — [LinkedIn Help 50191](https://www.linkedin.com/help/linkedin/answer/50191)
- Not available on mobile. Download only on a personal computer. You get only the categories that apply to your account, so with no certifications there is no certifications file. People You May Know and Who's Viewed Your Profile are not included. Data outside the standard files needs the Data Access Request Form, which takes "several days". [official] — [LinkedIn Help 50191](https://www.linkedin.com/help/linkedin/answer/50191)
- **Programmatic access (Member Portability API) exists only for EU/EEA/Switzerland members.** [official] — [LinkedIn Help 50191](https://www.linkedin.com/help/linkedin/answer/50191)
- Format: a ZIP with a mix of CSV, JSON and sometimes HTML-like files. Files listed include Connections.csv, Profile.csv, Jobs.csv, Invitations.csv, SearchHistory.csv, Endorsements_Received.csv, Recommendations_Given/Received.csv and a Messages/ directory. The guide was updated 2026-09-28 and last verified 2026-09-03. [secondary] — [TakeoutDay guide](https://takeoutday.org/guides/how-to-export-linkedin-data)

**Carteira de Trabalho Digital (CTPS Digital, MTE)**
- The employer's eSocial submission *is* the signature of the work card: "O envio dessas informações ao eSocial terá valor de assinatura de carteira". The app shows only "empregado" and "empregado doméstico" relationships, and CNIS data not in the app must be viewed in Meu INSS. [official, FAQ updated 30/08/2024, possibly outdated] — [MTE FAQ CTPS Digital](https://www.gov.br/trabalho-e-emprego/pt-br/servicos/trabalhador/carteira-de-trabalho/perguntas-frequentes-carteira-de-trabalho-digital)
- First access shows personal data plus the last 3 events of the latest contract (admission, leave, vacation). Salaries and the whole working life ("toda a vida laboral") need extra validation: 4 of 5 security questions, facial validation in the gov.br app, or bank/certificate validation. [official] — [MTE FAQ](https://www.gov.br/trabalho-e-emprego/pt-br/servicos/trabalhador/carteira-de-trabalho/perguntas-frequentes-carteira-de-trabalho-digital)
- Limitations: it shows the **CBO occupation code/name, not the company's job title**. Old contracts are more likely to have errors in title, pay and dates. Relationships recognised by the Labour Court (eSocial events S-2500/S-8200) did not appear yet. It is valid to prove employment but "não é válida como documento de identificação". Keep the physical CTPS for pre-2019 contracts. Legal basis cited: Portaria MTP nº 671/2021. [official] — [MTE FAQ](https://www.gov.br/trabalho-e-emprego/pt-br/servicos/trabalhador/carteira-de-trabalho/perguntas-frequentes-carteira-de-trabalho-digital)
- Data provenance conflict: an MTE 2022 press release says contract data comes from CNIS and eSocial, while the FAQ says CNIS data is not shown in the app. — [MTE news 2022](https://www.gov.br/trabalho-e-emprego/pt-br/noticias-e-conteudo/2022/outubro/carteira-de-trabalho-digital-alcanca-mais-de-1-bilhao-de-acessos-em-3-anos-de-lancamento) vs [MTE FAQ](https://www.gov.br/trabalho-e-emprego/pt-br/servicos/trabalhador/carteira-de-trabalho/perguntas-frequentes-carteira-de-trabalho-digital)
- **PDF export**: secondary sources describe exporting contracts as a PDF from the app ("selecionar todos, alguns ou apenas um" contract, or a "Enviar" tab). The official FAQ does not describe export and **does not mention any API**. [secondary] — [Politize](https://www.politize.com.br/carteira-de-trabalho-digital/); [UFES guide PDF](https://residenciamedica.ufes.br/sites/residenciamedica.ufes.br/files/field/anexo/carteira_de_trabalho.pdf); [MTE FAQ (no export/API)](https://www.gov.br/trabalho-e-emprego/pt-br/servicos/trabalhador/carteira-de-trabalho/perguntas-frequentes-carteira-de-trabalho-digital)

**Meu INSS — Extrato CNIS (the best salary-history source)**
- The extract "informa todos os seus vínculos, remunerações e contribuições previdenciárias". It comes in 3 types: *Relações Previdenciárias* (periods), *Relações Previdenciárias e Remunerações* (periods + pay amounts) and *Ano Civil* (contributions per year, from 11/2019). It is free, fully online (Meu INSS app or gov.br/meuinss), can be downloaded at request time, and needs a gov.br **Bronze, Prata or Ouro** account. [official] — [gov.br service: Emitir Extrato de Contribuição (CNIS)](https://www.gov.br/pt-br/servicos/emitir-extrato-de-contribuicao-cnis)
- In practice it downloads as a PDF ("Baixar PDF"/"Baixar Documento"). Choose the "Vínculos, contribuições e remunerações" version for salaries. Corrections go through "Atualizar vínculo, remuneração e CNIS". [secondary] — [Ingracio Advocacia](https://ingracio.adv.br/como-imprimir-o-cnis/); [UENF guide 2026](https://uenf.br/dga/grh/files/2026/06/Como-emitir-CNIS.pdf)

**Informe de rendimentos + IRPF pre-filled return (Receita Federal)**
- The pre-filled return auto-fills income, deductions, assets/rights, debts. The data comes from third parties (employers, health providers, real estate agencies, notaries, banks), so the taxpayer must check it. New in 2026: variable-income withholding, domestic-employee data from eSocial, DARF payment recovery, and alerts. [official] — [Ministério da Fazenda, IRPF 2026 rules](https://www.gov.br/fazenda/pt-br/assuntos/noticias/2026/marco/receita-federal-anuncia-regras-para-declaracao-do-imposto-de-renda-da-pessoa-fisica-2026); [Receita, abril 2026](https://www.gov.br/receitafederal/pt-br/assuntos/noticias/2026/abril/receita-federal-amplia-simplificacao-do-imposto-de-renda-e-prepara-novas-melhorias-para-os-proximos-anos)
- The IRPF 2026 filing window ran 23 March to 29 May 2026. The pre-filled return was used in 59.8% of returns filed, a record. [official] — [Fazenda, prazo](https://www.gov.br/fazenda/pt-br/assuntos/noticias/2026/marco/receita-comeca-a-receber-declaracoes-do-ir-na-proxima-segunda-23-3-e-prazo-vai-ate-29-de-maio); [Receita, junho 2026](https://www.gov.br/receitafederal/pt-br/assuntos/noticias/2026/junho/irpf-2026-registra-recorde-de-entrega-de-declaracoes)
- It requires a gov.br **Prata or Ouro** account; Bronze is not enough. [secondary] — [B3 Bora Investir](https://borainvestir.b3.com.br/noticias/imposto-de-renda/ir-2026-declaracao-pre-preenchida-exige-conta-gov-br-saiba-como-ter-nivel-prata-ou-ouro/)
- The DIRF was abolished. Payer data now reaches Receita monthly via **eSocial** (employment) and **EFD-Reinf** (payments to individuals without employment). In 2026 there were mismatches between the pre-filled return and employers' informes. [secondary] — [COAD](https://www.coad.com.br/home/noticias-detalhe/132576/com-o-fim-da-dirf-empregadores-devem-estar-atentos-as-obrigacoes-relativas-ao-esocial-e-a-efd-reinf); [Folha PE](https://www.folhape.com.br/economia/divergencias-no-esocial-elevam-risco-de-malha-fina-no-ir-2026/489677/)
- The payer (employer/bank) must provide the informe by the last business day of February (27/02/2026 this year), per IN RFB 698/2006 as reported by the press. [secondary] — [Jornal Contábil](https://jornalcontabil.com.br/noticia/termina-hoje-o-prazo-para-entregar-informes-de-rendimento-para-ir-2026/); [InfoMoney](https://www.infomoney.com.br/minhas-financas/imposto-de-renda-2026-informe-de-rendimentos-antes-neste-ano/)

**University (UFRGS) and diplomas**
- UFRGS: the printable transcript comes from Portal do Aluno → Informações do Aluno → Histórico Escolar. The **electronically authenticated** transcript comes from Portal do Aluno → Documentos → Históricos. "Histórico do curso" (current curriculum only) is different from "histórico escolar" (everything taken at UFRGS). [official, unit pages] — [UFRGS Biociências](https://www.ufrgs.br/biociencias/historico-escolar/); [UFRGS Instituto de Artes](https://www.ufrgs.br/institutodeartes/?p=10913)
- UFRGS requests colação de grau in Portal do Aluno "para expedição e registro do diploma digital". [official] — [UFRGS Instituto de Artes, Diplomação](https://www.ufrgs.br/institutodeartes/?p=12814)
- The MEC Diploma Digital is an **XML signed with XAdES** (Portaria MEC 554/2019, art. 6) using ICP-Brasil certificates. The institution must give the graduate a restricted area to download the visual representation and the XML. The ITI validator checks CAdES/XAdES/PAdES. Portaria MEC 70/2025 amended 554. [official/secondary mix] — [Portaria MEC 554/2019 (ABMES copy)](https://abmes.org.br/public/arquivos/legislacoes/Portaria-MEC-554-2019-03-11.pdf); [RNP Diplomas Digitais FAQ](https://ajuda.rnp.br/diplomas-digitais/perguntas-frequentes); [UFMS authenticity guide](https://prograd.ufms.br/files/2023/11/Guia-de-afericao-de-autenticidade-do-diploma-digital.pdf); [Portaria MEC 70/2025](https://www.lex.com.br/portaria-mec-no-70-de-24-de-janeiro-de-2025/)

**Structured CV format**
- JSON Resume schema v1.7.1, all sections optional: basics, work, volunteer, education, awards, **certificates** (name, date, issuer, url, credentialId, **expiryDate**, summary), publications, skills, languages, interests, references, projects, meta. work = name, position, description, location, url, startDate, endDate, summary, highlights, keywords. education = institution, area, studyType, startDate, endDate, score, courses. It has a CLI (`resume validate`) and themes, and editors validate via `$schema`. [official] — [jsonresume.org/schema](https://jsonresume.org/schema)

### Inferences
- **Brazil has no "connect" button for career data.** LinkedIn's API portability is EU-only, MTE documents no CTPS API, and Meu INSS/Receita are PDF downloads behind gov.br login. Career should be built around **dropping files into an inbox**: LinkedIn ZIP, CNIS PDF, CTPS PDF, informe PDFs, UFRGS authenticated transcript PDF, diploma XML + RVDD PDF. Each file gets a parser that proposes structured records the user confirms. Do not plan scraping of gov.br, since it uses facial/biometric step-ups.
- **The canonical salary history should come from the CNIS "Relações Previdenciárias e Remunerações"**: one row per relationship per month with pay. Cross-check it against informes (annual totals per CNPJ) and, optionally, salary credits in the bank data already flowing through Pluggy in the Finanças app (memory context, not a cited source). Keep CTPS Digital as the contract/event layer (admission, leave, vacation, CBO).
- **Career data model:** JSON Resume as the export/interchange shape (work, education, certificates with expiryDate, skills, projects), extended with Brazil fields: CNPJ, CBO code, regime (CLT/PJ/estágio), source document id, monthly remuneration series, yearly informe totals. LinkedIn Positions/Education/Skills/Certifications map directly onto JSON Resume sections.
- **Keep the originals.** Each normalized record should point back to the source file (CNIS PDF version/date, diploma XML). Signed artefacts (diploma XML, authenticated transcript, gov.br PDFs with QR codes) are worth more as originals than as parsed text.
- The tax/income part of Career overlaps with Finanças. The informe and IRPF receipts probably belong to one "annual tax folder" per year shared by both apps, not duplicated.

### Gaps
- No official page found listing the **CSV column names** of LinkedIn's Positions/Education/Skills/Certifications files. Search snippets claimed Positions.csv has company, title, description, location, start/end dates, and that LinkedIn sometimes adds note lines above the CSV header and renames columns. **Unverified**; build the parser defensively.
- Official confirmation of the CTPS Digital PDF export (menu names, whether the PDF carries a QR/authenticity code) was not found. Only secondary sources from 2019–2025.
- Whether CNIS "remunerações" show the full salary or the contribution salary capped at the INSS ceiling (teto) was not verified. This matters for using CNIS as a true salary history. Holerites/informes may be needed for above-ceiling pay.
- Receita has no API for the pre-filled return for individuals. The data is available inside the IRPF program / Meu Imposto de Renda (e-CAC) after gov.br Prata/Ouro login. The exact export formats (the .DEC/.REC files of the declaration program) were not researched.
- UFRGS-specific diploma-digital download and validation steps (and whether UFRGS issues the XML for older graduates) were not found. Ask UFRGS's Secretaria de Registro de Diplomas.

## Q2. How career tools present a career timeline, and what a personal Career app should hold

### Takeaway
Three patterns dominate. The **profile/timeline** (LinkedIn positions, JSON Resume work/education arrays rendered by themes). The **master resume / achievement library** (Teal: keep every experience and metric-driven bullet once, then pick per CV version). The **running brag document** (Julia Evans: goals, projects with impact, collaboration, learning, updated every 2 weeks to every 6–12 months). Job-search trackers (Huntr, Teal) add an application pipeline, which is less relevant for a personal archive.

### Cited Findings
- The brag document (Julia Evans, 2019-06-28) has sections: goals this year/next year, projects (contribution + impact, numbers, revisit after launch), collaboration & mentorship, design & documentation, company building, what you learned, outside of work (talks, OSS). You can update it every 2 weeks or in a "single marathon session every 6 months or every year". Share it with managers and peer reviewers, and make work sound "exactly as good as it is". — [jvns.ca: Get your work recognized](https://jvns.ca/blog/brag-documents/)
- Teal pitches a **master resume** that "stores your complete career history in one place" (internships, coursework, projects, volunteering), with an "Achievement Assistant" for metric-driven bullets. [vendor] — [Teal: master resume](https://www.tealhq.com/post/how-to-create-a-master-resume)
- Teal imports career history from LinkedIn or an uploaded resume, lets you tick what goes into each resume version, has a free plan with unlimited resumes/job tracking, and Teal+ costs about $9/week. [third-party review, pricing may be outdated] — [Resume Genius review](https://resumegenius.com/reviews/teal-resume-builder-reviews)
- Huntr vs Teal: Huntr "favors speed and visibility" in application tracking, while Teal "favors structure and oversight". Both improve an existing resume rather than build from scratch. [vendor-authored, not neutral] — [Huntr blog](https://huntr.co/blog/huntr-vs-teal)
- JSON Resume separates data (schema) from presentation (themes, CLI). Certificates carry `expiryDate`, which suits a timeline that flags expiring credentials. — [jsonresume.org/schema](https://jsonresume.org/schema)

### Inferences
- **Recommended Career layout (desktop-first):**
  1. **Timeline**: a horizontal or vertical lane per track (Education, Employment, Certifications, Side projects), built from JSON-Resume-shaped records, with salary as a step line from CNIS monthly remunerations under the employment lane.
  2. **Record detail**: each position/course with its source documents attached (CTPS contract PDF, CNIS row, informe, transcript, diploma).
  3. **Brag log**: dated entries (project, impact metric, link) tied to a position, written continuously and rolled up per review period.
  4. **CV export**: choose entries/bullets, then JSON Resume, then theme/PDF, following the Teal "master resume, tick what to include" pattern.
  5. **Yearly folder**: informe(s) + IRPF receipt per calendar year.
- Job-application tracking (Huntr/Teal pipelines) is optional and could come later as a kanban. It is not core to "gather my career records".
- The brag log is the only part the user writes by hand. Everything else should be derived from uploaded documents, which keeps maintenance low.

### Gaps
- No primary documentation found for how Huntr or Teal visualise a *career timeline*. Both are job-search tools, and the sources only compare trackers and resume builders.
- No neutral comparison of JSON Resume themes for timeline rendering was gathered.

## Q3. Wallet product patterns: phone wallets, Brazilian digital documents, document managers, password managers, expiry rules

### Takeaway
Phone wallets separate **low-sensitivity passes** (tickets, boarding passes, loyalty: barcodes, relevance by date/location) from **private passes / IDs** that need re-verification on every view and stay out of personalization and the web UI. Brazil's official digital IDs live in the **gov.br app "Carteira de documentos"** (CPF, CIN, CNH, CHT, military certificates). They can be shared as PDFs with a QR authenticity check, and the CIN has its own QR verifier. Password managers (Bitwarden/Vaultwarden, 1Password) already offer typed ID items (passport, driver license) plus encrypted attachments, which is the closest existing product to "Wallet must be secure".

### Cited Findings

**Apple Wallet (PassKit)**
- A pass is a "digital representation of information that might otherwise be printed on small pieces of paper or plastic". The system has three parts: a package format, a web service for updates (push), and an app API. [official, archive docs] — [Wallet Developer Guide intro](https://developer.apple.com/library/archive/documentation/UserExperience/Conceptual/PassKit_PG/index.html)
- Styles: `boardingPass`, `coupon`, `eventTicket`, `storeCard`, `generic`. The package is `pass.json` + images + `manifest.json` (SHA-1 of each file) + `signature` (PKCS#7 detached, includes WWDR intermediate), zipped. `passTypeIdentifier` and `teamIdentifier` must match the signing certificate. There is up to one `relevantDate` and up to 10 `locations`/beacons. Relevance is passive (no notifications). [official, archive docs] — [PassKit_PG: Creating](https://developer.apple.com/library/archive/documentation/UserExperience/Conceptual/PassKit_PG/Creating.html)

**Google Wallet**
- **Private passes** contain sensitive data, may require fingerprint/PIN to add, open and use, and are not used for personalization or form-filling by default. Photo-created passes containing sensitive data are classified as private. — [Google Wallet Help: pass classification](https://support.google.com/wallet/answer/14595878?hl=en)
- "Everything Else": create a pass from a photo, with the original photo kept below the pass. Private passes such as IDs and health insurance cards are **not visible on the Google Wallet website**. Not available in India. — [Google Wallet Help: manage items](https://support.google.com/wallet/answer/12060038?hl=en)
- Issuers: the **Generic Private Pass** vertical (health insurance, national IDs, government IDs) needs explicit Google approval and uses JWT-only issuance. Sensitive PII is barred from the standard Generic pass. — [Google Developers: Generic Private Pass](https://developers.google.com/wallet/generic-private-pass); [Generic pass overview](https://developers.google.com/wallet/generic)

**Brazilian official digital documents**
- gov.br app → "Carteira de documentos", which needs a **Prata or Ouro** account, holds: CPF Digital, **CIN**, **CNH Digital** (generated first in the traffic app), **CHT** (ANAC), and the military CDI, CAM and CR certificates. More are promised. Documents can be **shared as PDF with a QR code authenticity check**. [official, no update date] — [Governo Digital: Carteira de documentos digitais](https://www.gov.br/governodigital/pt-br/identidade/carteira-de-documentos-digitais)
- CIN validity (Decreto 10.977/2022): 5 years (ages 0–12), 10 years (12–60), no expiry over 60. The old RG "continua válido por 10 anos… até 2032". The QR code is verified with a free reader app (partial offline / full online), and "somente a última CIN emitida terá o QR Code válido". [official, updated 16/07/2026] — [CIN FAQ](https://www.gov.br/governodigital/pt-br/identidade/cin/perguntas-frequentes-sobre-a-cin)
- CIN adoption reached 45 million people by Feb 2026. — [Agência Gov](https://agenciagov.ebc.com.br/noticias/202602/nova-carteira-de-identidade-alcanca-45-milhoes-e-amplia-o-acesso-ao-numero-de-identificacao-unico)
- The Carteira Digital de Trânsito app became "CNH do Brasil" (Serpro). [official] — [Serpro: CNH do Brasil](https://www.serpro.gov.br/menu/noticias/revista-tema-240/cnh-do-brasil); [gov.br: CNH-e](https://www.gov.br/pt-br/servicos/emitir-a-carteira-nacional-de-habilitacao-digital-cnh-e)
- CNH validity (Lei 14.071/2020, in force 12/04/2021): up to 10 years under 50, 5 years for 50–69, 3 years for 70+. It applies from the next renewal, and a doctor can shorten it. [secondary] — [Jornal Contábil](https://jornalcontabil.com.br/noticia/novas-regras-da-cnh-ja-estao-valendo/); [Detran-ES e-book](https://detran.es.gov.br/Media/detran/Outros%20Downloads/E-BOOK%20AND.pdf)
- Brazilian passport: 10 years for adults. For minors validity follows age (1–5 years). 4 years if the previous passport is lost or not presented. Emergency passport up to 1 year. Validity cannot be extended. [official] — [Polícia Federal: validade do passaporte](https://www.gov.br/pf/pt-br/assuntos/passaporte/ajuda/duvidas_/caderneta/caderneta-validade-do-passaporte)

**Password managers holding documents**
- Bitwarden attachments are "encrypted and decrypted locally". Limits: up to 500 MB per file (100 MB from mobile) and 5 GB per account (self-hosted: limited by disk, up to 10 TB). Attachments are a Premium/paid-org feature. Export includes attachments only as ".zip (with attachments)" from the individual vault. [official] — [Bitwarden Help: attachments](https://bitwarden.com/help/attachments/)
- Bitwarden crypto: each item has its own random Cipher Key wrapped by the user key. For attachments, the Cipher Key encrypts the file name/size and a separate **Attachment Key** that encrypts the data. KDF is PBKDF2-SHA256 at 600,000 iterations by default, or Argon2id. "Bitwarden never stores and cannot access your master password or your cryptographic keys." [official] — [Bitwarden Security Whitepaper](https://bitwarden.com/help/bitwarden-security-white-paper/)
- 1Password item categories include **Document** ("upload your important files"), **Passport** (issuing country, number, name, nationality), **Driver License** (number, name, **expiry date**), Identity and Membership. [official] — [1Password: item categories](https://support.1password.com/item-categories/)

**Document managers**
- Paperless-ngx: "**should never be run on an untrusted host** because information is stored in clear text without encryption… The safest way to run Paperless-ngx is on a local server in your own home with backups." [official README] — [paperless-ngx README](https://github.com/paperless-ngx/paperless-ngx)
- Paperless-ngx **v3.0.0 (2026-07-22): "[BREAKING] Remove support for document and thumbnail encryption"** (PR #11850). Paperless-ng had already stopped encrypting new documents in 0.9.3 (2020). The latest release is v3.4.2 (2026-11-03). [official] — [v3.0.0 release](https://github.com/paperless-ngx/paperless-ngx/releases/tag/v3.0.0); [PR #11850](https://github.com/paperless-ngx/paperless-ngx/pull/11850); [paperless-ng 0.9.3](https://github.com/jonaswinkler/paperless-ng/releases/tag/ng-0.9.3)
- Rationale quoted from the README in a community thread: the server must read documents unencrypted, so on-disk encryption would require storing the key too. [community] — [r/selfhosted "Security for a selfhosted DMS" (mirror)](https://lr.eu.psf.lt/r/selfhosted/comments/mkpby0/security_for_a_selfhosted_dms)
- Mayan EDMS reportedly has a pass-through `encryptedstorage` backend for documents, previews and cache, but this is **unverified in official docs**. [community] — [Mayan forum](https://forum.mayan-edms.com/t/how-to-enable-encryption/1847)
- "Family Vault": a new open-source self-hosted ID/passport vault (AES-256-GCM, Docker + PostgreSQL + MinIO), created February 2026. It is immature, so treat it as a reference only. [aggregator] — [awesome.ecosyste.ms entry](https://awesome.ecosyste.ms/projects/github.com%2Fdeadsec-security%2Ffamily-vault)

### Inferences
- **What Wallet should hold, by tier:**
  - **Passes** (low sensitivity): event tickets, boarding passes, reservations. Keep the original `.pkpass`/PDF/QR image plus parsed fields (event, venue, date/time, seat, PNR, barcode payload). Surface them on the phone around `relevantDate`, which mirrors Apple/Google relevance.
  - **Identity documents** (high sensitivity): CIN, CNH, passport, CPF, título, reservista, birth/marriage certificates, diplomas. Store a front/back scan or the official gov.br PDF (QR-verifiable), plus typed fields modelled on 1Password's categories (number, issuer, issue/expiry, holder).
  - **Cards** (high sensitivity): do *not* store full PAN/CVV in Odysseus. Store last-4, issuer, expiry and a pointer to the password manager. Card data has the least upside and the highest abuse value.
- **Expiry engine**: compute or suggest expiry from Brazilian rules, then remind well in advance. Passport 10 years (adult). CNH 10/5/3 years by age band at renewal. CIN 5/10/none by age. Old RG valid until 2032. Certificates use JSON Resume `expiryDate`. Expiry dates and document *types* can live as non-sensitive metadata even when the file itself is end-to-end encrypted, so reminders work without unlocking.
- **Do not try to issue Apple/Google wallet passes for IDs.** Apple signing requires a Pass Type ID certificate tied to an Apple Developer team, and Google private passes need issuer approval. Re-opening the airline's or event's original `.pkpass` on the phone is enough. The official Brazilian ID stays in the gov.br app, with Odysseus keeping only an archival copy.
- **Paperless-ngx is a fine Career/"papers" backend (OCR, tagging) but a poor Wallet backend.** It has no at-rest encryption since v3.0, and anything readable by the server is readable by an agent with shell access.

### Gaps

## Q4. Security architecture for a self-hosted sensitive-document vault (encryption, step-up unlock, audit, AI exclusion, backups, threat model with a shell-capable agent)

### Takeaway
Server-side encryption, Paperless-ngx (no encryption since v3.0) and Nextcloud SSE (server holds keys) **do not protect against anything running on the same host**, and Odysseus's AI agent has shell in the same container. Only **client-side / end-to-end encryption, with keys never present on the server or in the agent's filesystem/env**, keeps ID scans out of the agent's reach. Even then, an agent that can modify the code served to the browser can capture the key on the next unlock. The practical choices are: (a) store Wallet secrets in **Vaultwarden on the NAS** (mature E2E, native phone apps, OIDC SSO since 1.35), or (b) build an Odysseus "sealed" store with browser-side WebCrypto + passphrase/WebAuthn-PRF unlock, served from a code path the agent cannot write. Both need step-up re-auth for viewing, an append-only audit log outside the container, and age-encrypted offsite backups.

### Cited Findings

**Server-side vs end-to-end options**
- Nextcloud SSE is "mainly for protecting files on external, third-party storage". It "does not protect data from a compromised Nextcloud server or malicious administrator". Keys are stored on the server, and in master-key mode "Admins can decrypt any user's files". Filenames, folder structure, trash, versions, thumbnails, previews and the search index are **not** encrypted. Overhead is about 1% (35% before NC 25). LUKS is suggested for physical theft. [official] — [Nextcloud admin: encryption configuration](https://docs.nextcloud.com/server/latest/admin_manual/configuration_files/encryption_configuration.html)
- Nextcloud E2EE: desktop/Android/iOS clients encrypt. In the browser, "E2EE folders are currently read-only", and you cannot add, edit or share them or enable encryption on a folder. Encryption only works on empty folders. The mnemonic is the only recovery ("If you lose access to your mnemonic, you will lose access to your files"). [official] — [Nextcloud user manual: using E2EE](https://docs.nextcloud.com/server/latest/user_manual/en/files/using_e2ee.html)
- Inside E2EE folders you also lose public/group shares, server-side search and previews, and server-side trash and versioning. [secondary] — [Linuxfabrik](https://www.linuxfabrik.ch/en/blog/nextcloud-server-side-und-end-to-end-encryption)
- Cryptomator: per-vault 256-bit encryption + MAC masterkeys from a CSPRNG, wrapped with AES Key Wrap (RFC 3394) under a scrypt-derived KEK. `masterkey.cryptomator` stores the scrypt params/salt in plaintext, and `vault.cryptomator` is a JWT readable without a key (format, cipher combo, vault UUID). "No unencrypted copies on your hard disk drive." Hub-managed vaults deliver the masterkey per user as a JWE (ECDH-ES). [official] — [Cryptomator security architecture](https://docs.cryptomator.org/security/architecture/)
- age v1.3.2: "simple, modern and secure file encryption tool, format, and Go library". It supports X25519, ssh-ed25519/rsa recipients, passphrase mode, **post-quantum hybrid ML-KEM keys** (`age-keygen -pq`, v1.3.0+), `age-plugin-yubikey` for hardware PIV keys, and recipients files (`-R`). Spec at age-encryption.org/v1. [official] — [FiloSottile/age](https://github.com/FiloSottile/age)
- Bitwarden attachments: client-side encryption with a per-attachment key (see Q3). [official] — [Bitwarden whitepaper](https://bitwarden.com/help/bitwarden-security-white-paper/)
- Vaultwarden backup set: `db.sqlite3` (required), `attachments/` (required, "stored as separate files"), `sends/` (optional), `config.json` and `rsa_key*` (recommended). Back up SQLite with `.backup`, `VACUUM INTO` or `/vaultwarden backup` (since 1.32.1). Encrypt backups. [official wiki] — [Vaultwarden: Backing up your vault](https://github.com/dani-garcia/vaultwarden/wiki/Backing-up-your-vault)
- Vaultwarden config has `USER_ATTACHMENT_LIMIT`/`ORG_ATTACHMENT_LIMIT` (KB) and `SENDS_ALLOWED`, plus **OIDC SSO** (`SSO_ENABLED`, `SSO_ONLY`, `SSO_AUTHORITY`, `SSO_PKCE=true`…). 2FA options include Duo/Yubico/email and `TWO_FACTOR_REMEMBER_DAYS=30` by default. [official] — [Vaultwarden .env.template](https://github.com/dani-garcia/vaultwarden/blob/main/.env.template)
- SSO arrived in Vaultwarden release 1.35.0 (2025-12-27). The latest is 1.37.5 (2026-11-01). The README lists Attachments, Send, Organizations and Personal Vault as supported. [official] — [Vaultwarden 1.35.0](https://github.com/dani-garcia/vaultwarden/releases/tag/1.35.0); [1.37.5](https://github.com/dani-garcia/vaultwarden/releases/tag/1.37.5); [README](https://github.com/dani-garcia/vaultwarden)

**Unlock / step-up**
- OWASP: require re-authentication before sensitive operations, using "an authenticator already bound to the account, such as the current password or a passkey". Do not use security questions. "Invalidate sessions after re-authentication and rotate tokens." Adaptive auth uses device/IP as "risk signals, not as substitutes for authentication", and sensitive data may need "stronger or fresher authentication". [official] — [OWASP Authentication Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html)
- The WebAuthn **PRF** extension lets a web app derive a deterministic 32-byte secret from a passkey/security key during authentication, usable as a WebCrypto key. It needs support from the authenticator, the OS and the browser together. [vendor] — [Corbado: PRF](https://www.corbado.com/blog/passkeys-prf-webauthn); [Bitwarden: PRF](https://bitwarden.com/blog/prf-webauthn-and-its-role-in-passkeys/)
- Bitwarden shipped passkey-based vault unlock via PRF in beta for Chromium browsers (Nov 2025). Passkeys without PRF still log in but need the master password to decrypt. [press] — [Help Net Security](https://www.helpnetsecurity.com/2025/11/19/bitwarden-browser-extensions/)
- Google Wallet's private-pass model (verify on every view, no web visibility, no personalization use) is a consumer-product precedent for "unlock to view". — [Google Wallet Help](https://support.google.com/wallet/answer/14595878?hl=en); [manage items](https://support.google.com/wallet/answer/12060038?hl=en)

**AI-agent threat model**
- Lethal trifecta: an agent with (1) access to private data, (2) exposure to untrusted content, and (3) the ability to communicate externally can be prompt-injected into exfiltrating data. "The only way to stay safe there is to avoid that lethal trifecta combination entirely". Guardrail vendors are suspect, since "95% is very much a failing grade". [primary blog] — [Simon Willison, 2025-06-16](https://simonwillison.net/2025/Jun/16/the-lethal-trifecta/)
- OWASP LLM06:2025 Excessive Agency names three root causes (excessive functionality, permissions, autonomy) and recommends human approval of high-impact actions. [official] — [OWASP LLM06:2025](https://genai.owasp.org/llmrisk/llm062025-excessive-agency/)
- OWASP AI Agent Security Cheat Sheet: a separate policy/execution component should validate scope, privilege and approval state, rather than trusting the agent. Approvals should be bound to actor/tool/target/parameters/expiry and consumed once. [official] — [OWASP AI Agent Security Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/AI_Agent_Security_Cheat_Sheet.html)

### Inferences
- **Threat model in one line.** The Odysseus agent reads web pages, mail and files (untrusted content), can make HTTP requests (external comms) and has shell in the app container. Putting plaintext ID scans, or keys that decrypt them, anywhere the container can read **completes the lethal trifecta**. A "no AI access by default" toggle in app code does not stop a shell-capable agent from running `cat`/`sqlite3` on the files.
- **What does *not* help against the agent:** Nextcloud SSE (server keys); app-level encryption with the key in env/secrets mounted into the same container (the Paperless rationale applies); LUKS/disk encryption (it only protects powered-off disks). These help only against theft and offsite-storage threats.
- **What does help:** ciphertext-only storage where the decryption key exists only in the user's browser/device at view time (Bitwarden/Vaultwarden model, Nextcloud E2EE model, age with an identity that never touches the container). Plus **separation**: vault data and keys on the NAS in a different container/user that the Odysseus container has no mount or credentials for.
- **Residual risk to call out:** with browser-side decryption, whoever controls the JavaScript served to the browser can steal the key at unlock time. If the agent can edit Odysseus's static files or templates in the running container, it can plant a key-logger. Mitigations: read-only root filesystem for the app container (memory notes code is baked into the image, so this is feasible), serving the vault UI from a separate origin/container on the NAS that the agent cannot write, or using Bitwarden's native apps/extension, whose code the server does not deliver.
- **Recommended architecture (two viable paths):**
  - **Path A, pragmatic (recommended first):** run **Vaultwarden on the NAS** as the Wallet's secure store. Use typed items (identity/card/secure note) + encrypted attachments for ID scans and passport, SSO via the NAS OIDC provider, and a passkey/2FA. Phone access comes from the official Bitwarden app (offline cache). Odysseus Wallet then holds only **non-sensitive metadata**: document type, holder, issuer, expiry date, last-4, a deep link to the Vaultwarden item. Reminders and the agent can use that metadata safely. Low build cost and mature crypto. Trade-off: the documents themselves are viewed outside Odysseus.
  - **Path B, native "sealed" tier in Odysseus:** the browser encrypts each file with a random per-file key (AES-GCM via WebCrypto), wrapped by a vault key. The vault key is unlocked by a passphrase (Argon2id/scrypt) and/or **WebAuthn PRF** (passkey on phone and laptop), with a printed recovery key. The server and NAS store only ciphertext plus a plaintext metadata row. Viewing requires a **fresh step-up** (OWASP), the key lives in memory only for N minutes, and nothing is ever sent to the agent/LLM. Requires a read-only app container or a separate origin, as above.
- **Tiering for both apps:** Tier 0 (metadata, expiries, timeline facts: agent-readable). Tier 1 (career papers: transcripts, CNIS, informes, CVs. Server-readable, encrypted at rest on disk/backups, agent access **opt-in per document**, because these contain CPF and salary). Tier 2 (IDs, passport, card data, gov.br PDFs. E2E only, never agent-readable, step-up to view).
- **Audit log:** append-only events (unlock, view, download, export, failed step-up) written to the NAS (outside the Odysseus container), shown in the Wallet UI. An agent with shell in the app container must not be able to rewrite it.
- **Backups:** Vaultwarden per its wiki (`db.sqlite3` via `/vaultwarden backup` + `attachments/` + `rsa_key*` + `config.json`). Odysseus sealed blobs are already ciphertext. Wrap backup archives with **age** to a recipient whose identity is offline (paper/YubiKey via `age-plugin-yubikey`), optionally a PQ hybrid recipient. Keep 3-2-1 with one offsite copy, and test restores. Back up the E2E recovery key/mnemonic separately, since losing it loses the data, the same as Nextcloud E2EE.
- **Cryptomator** is a reasonable *file-level* option for a folder of scans synced via Nextcloud. Plaintext only exists on unlocked clients. But it has no web UI for Odysseus and leaks size/count/structure metadata (unverified, see Gaps). It fits better as a backup/archive format than as the Wallet store.
