# Hub navigation: organizing and integrating many personal-data apps in one window (Life hub, Odysseus)

Research date: 2026-11-06. Dates are given for every source; anything before 2025 is labeled "older" where it matters. Where a page could not be fetched directly (Material 3 site and Apple HIG HTML are JS-rendered; some news sites returned 403), I used the implementing library docs (material-components-android), Apple's HIG JSON endpoints, or search-result summaries, and say so inline.

## Q1. Navigation with ~9 destinations: rail vs drawer vs sidebar, labels, grouping, collapsing, phones

### Takeaway
Nine destinations is above every "bar" limit (3–5) and above the collapsed-rail limit (max 7), so both Material 3 and Apple point to an expanded, text-labeled vertical list (M3 "expanded rail", which replaced the drawer in 2025; Apple "sidebar") on wide windows, with at most light grouping. Icon-only collapsed rails are acceptable only for frequently used apps with clear icons. On phones the platforms say: bottom bar of ≤5, avoid an overflow "More" tab, and use a sidebar/index for the rest.

### Cited Findings
**Material 3 / Android (implementation docs, current)**
- Navigation bar (bottom): "Navigation bars can have three to five destinations"; `BottomNavigationView` "does not support more than 5 menu items." — [material-components-android BottomNavigation.md](https://raw.githubusercontent.com/material-components/material-components-android/master/docs/components/BottomNavigation.md)
- Default label mode for both bar and rail: labels on all items only when there are ≤3 items; with ≥4 items only the selected item shows its label ("labeled" when 3 items or less, "selected" when 4 items or more). Other modes: labeled / selected / unlabeled. — [BottomNavigation.md](https://raw.githubusercontent.com/material-components/material-components-android/master/docs/components/BottomNavigation.md); [NavigationRail.md](https://raw.githubusercontent.com/material-components/material-components-android/master/docs/components/NavigationRail.md). (Note: this default conflicts with NN/g's "always label" guidance below.)
- Navigation rail: "displays three to no more than seven app destinations when collapsed"; when collapsed only top-level items show, "up to a limit of 7"; "There is no limit of items shown when expanded." — [NavigationRail.md](https://raw.githubusercontent.com/material-components/material-components-android/master/docs/components/NavigationRail.md)
- Expanded rail replaces the drawer: "The navigation rail can now be expanded to show more content, functioning similarly to a navigation drawer"; rails are "collapsed by default"; submenus (groups) and dividers "are only visible when expanded"; a header (FAB/logo) can be anchored on top; rails are for "tablet and desktop screens." — [NavigationRail.md](https://raw.githubusercontent.com/material-components/material-components-android/master/docs/components/NavigationRail.md)
- M3 Expressive (May 2025): rail gets collapsed and expanded states, expanded rail replaces the navigation drawer (modal and non-modal variants), rail intended for "medium, expanded, large, or extra-large window sizes"; 9to5Google notes phones are left without a drawer substitute. — [9to5Google, 2025-05-14](https://9to5google.com/2025/05/14/material-3-expressive-navigation/). SAP's Fiori-for-Android M3 guidance (seen via search snippet; page returned 403 to fetch) says the collapsed rail should be used only with up to seven destinations and the expanded rail beyond that. — [SAP Fiori M3 navigation rail usage](https://www.sap.com/design-system/fiori-design-android/v26-4/components/m3-standard-components/navigation-rail/usage)
- Adaptive switching: `NavigationSuiteScaffold` shows a "Navigation bar if the width or height is compact" and a "Navigation rail for everything else"; apps can override to a permanent navigation drawer at expanded width. — [Android Developers: Build adaptive navigation](https://developer.android.com/develop/ui/compose/layouts/adaptive/build-adaptive-navigation)
- Window-size breakpoints (width): compact < 600dp (99.96% of phones in portrait); medium 600–840dp; expanded 840–1200dp; large 1200–1600dp; extra-large ≥ 1600dp ("Desktop displays"). Size classes depend on the window, not the device ("not intended for isTablet-type logic"). — [Android Developers: Window size classes](https://developer.android.com/develop/ui/compose/layouts/adaptive/window-size-classes)

**Apple HIG (current; fetched via JSON)**
- Sidebar purpose: navigate "between areas of your app or top-level collections of content"; "A sidebar requires a large amount of vertical and horizontal space. When space is limited ... a more compact control such as a tab bar may provide a better navigation experience." — [HIG Sidebars](https://developer.apple.com/design/human-interface-guidelines/sidebars)
- Hierarchy: "In general, show no more than two levels of hierarchy in a sidebar"; deeper data → "a split view interface that includes a content list between the sidebar items and detail view"; group with disclosure controls; "use succinct, descriptive labels to title each group." — [HIG Sidebars](https://developer.apple.com/design/human-interface-guidelines/sidebars)
- Visibility/customization: "Consider letting people hide the sidebar" but "Avoid hiding the sidebar by default to ensure that it remains discoverable"; "When possible, let people customize the contents of a sidebar"; macOS: "Consider automatically hiding and revealing a sidebar when its container window resizes" and "Avoid putting critical information or actions at the bottom of a sidebar." — [HIG Sidebars](https://developer.apple.com/design/human-interface-guidelines/sidebars)
- Icons: "Consider using familiar symbols"; icon colors should "serve a clear purpose"; fixed colors used sparingly can clarify meaning (Mail's yellow VIP). — [HIG Sidebars](https://developer.apple.com/design/human-interface-guidelines/sidebars)
- Tab bars: "Avoid overflow tabs ... The More tab makes it harder for people to reach and notice content on tabs that are hidden"; "it's generally easier to navigate among fewer tabs ... consider a sidebar or a tab bar that adapts to a sidebar as an alternative for an app with a complex information structure"; if users choose their own tabs, "aim for a default list of five or fewer"; "Use a tab bar to support navigation, not to provide actions." — [HIG Tab bars](https://developer.apple.com/design/human-interface-guidelines/tab-bars)
- iPadOS 18+ "sidebar-adaptable" tab view: a tab bar that converts to a sidebar; "Both variations include a button that people can use to switch between them" and it "responds automatically to rotation and window resizing." — [HIG Sidebars](https://developer.apple.com/design/human-interface-guidelines/sidebars)

**NN/g research**
- Left vertical nav (Laubheimer, 2021-05-16): good for "broad or growing IAs, but takes up more space"; having more than 7–9 top-level categories "is okay, you just need to plan appropriately"; users look at the left half of the screen 80% of the time; text labels should always be present ("a word is worth a thousand pictures"); icon-only menus will most likely be ignored, though icon-first collapsed menus "may work for frequently used applications where users learn the categories over time"; put less important items at the bottom; "Visible navigation is the gold standard for both mobile and desktop." — [NN/g: Left-Side Vertical Navigation](https://www.nngroup.com/articles/vertical-nav/)
- Icon usability (Harley, 2014, older but still cited): "a text label must be present alongside an icon"; "Icon labels should be visible at all times"; hover-only labels add cost and fail on touch; only a few icons (home, print, search) are near-universal; a clock icon for history was recognized as a clock but "Not a single test participant clicked this icon." — [NN/g: Icon Usability](https://www.nngroup.com/articles/icon-usability/)
- Menu-design checklist (Laubheimer, 2024-06-07): show navigation on larger screens (no hamburger on desktop); "Failing to indicate the current location is probably the single most common mistake"; provide local navigation for related content; icons should be "additional supportive elements, rather than replacing clear text labels"; primary navigation goes "on the left in applications"; avoid cascading menus beyond two tiers. — [NN/g: Menu-Design Checklist](https://www.nngroup.com/articles/menu-design/)
- Hidden vs visible nav (Pernice & Budiu, 2016, older): 179 users, 6 sites; on mobile, a site with visible/combo nav got navigation used by 89% of users vs 44% for a site hiding nav behind a low-salience icon; visible navigation suits 4–5 top-level options. — [NN/g: Make Navigation Discoverable on Mobile](https://www.nngroup.com/articles/find-navigation-mobile-even-hamburger/)

**Design-system rule sets**
- AWS Cloudscape side navigation: three states (expanded with full labels; closed; collapsed "narrow navigation rail of icons, text labels are surfaced as tooltips"); "Keep groupings to a minimum"; "Avoid sections with only two links"; "Avoid using sections and expandable link groups in the same side navigation"; "Always ensure one link in the side navigation is active"; "Keep the side navigation open by default for returning users"; "Don't offer a navigation rail for occasional-use services, or where destinations can't be clearly represented by icons." — [Cloudscape: Side navigation](https://cloudscape.design/patterns/general/service-navigation/side-navigation/)

### Inferences
- Nine items fit a single expanded, labeled list without scrolling; grouping is optional. If grouping, use dividers (or one short header per group), not collapsible groups, and avoid 1–2-item groups (Cloudscape). A defensible order for Life: Diary on top as the "spine" (the day page that merges everything); then the record-type apps (Location, Media, People, Health); then money/work (Finances, Wallet, Career); AI usage last (meta/least frequent, per NN/g "less important at bottom"). Possible headers if wanted: "Day", "Records", "Money & work", "System" — but with Diary alone and AI usage alone, plain dividers are cleaner than headers.
- Labels: always show text labels (NN/g), even in a narrow state. Prefer an M3-style narrow rail with the label under the icon (≈72–80px) over a pure icon strip with tooltips; Cloudscape and NN/g allow icon-only only for frequent use with clearly iconizable destinations, and "Wallet" vs "Finances", "Career", "AI usage" are not self-evident icons.
- Width behavior inside the Life window: expanded labeled list when the Life window is wide (≥ ~840–1200px of window width, mirroring "expanded/large" classes), narrow labeled rail at medium widths, and a phone pattern below 600px. Base the switch on the Life window's width, not the device (Android window-size-class principle).
- Label clarity: "Wallet" vs "Finances" is a likely confusion pair; NN/g's "clear, specific, familiar labels" argues for distinct wording or a subtitle/tooltip clarifying (e.g., "Wallet — cards, IDs, passes" if that is what it holds).
- Phones: 9 > 5, and Apple explicitly discourages a "More" overflow. Best fit: the Life root screen on phone is an index/list of the 9 apps (Apple Health "Browse" / Google Fit "Browse" pattern, see Q2), each app opens as a pushed screen with a back affordance; optionally a small bottom bar with ≤4–5 fixed items (e.g., Today/Diary, Search, Apps) rather than 4 apps + "More".

### Gaps
- m3.material.io pages are JS-rendered and could not be fetched; M3 numbers above come from the official Android implementation docs (material-components-android) and secondary coverage. The SAP page was blocked (403); its "up to seven" claim is from a search snippet but matches the Android docs.
- No quantitative study found comparing labeled vs icon-only vertical rails in applications (NN/g evidence is mostly qualitative).

## Q2. How real multi-domain personal-data products navigate

### Takeaway
Health and life-tracking apps converge on three layers: a "Today/Summary" home with a few user-pinned items, a "Browse" index of all categories, and per-category detail pages; only 4–5 primary destinations are in the bar, the rest are reached via Browse or search. Recent changes (2024–2026) show both directions and their costs: Apple consolidated Photos into one screen (iOS 18) and backed off to tabs (iOS 26); Nextcloud hid its app bar behind a switcher (Hub 26, 2026) and users complained about extra clicks and lost apps.

### Cited Findings
**Apple Health**
- Tabs Summary, Sharing, Browse; Summary shows pinned metrics; since iOS 18 the user-selected section is called "Pinned" (formerly "Favorites"); Edit on Summary to pin/unpin; Browse lists categories (Activity, Heart, Nutrition, Mental Wellbeing, ...) each opening data, articles, subcategories. — [iGeeksBlog guide (secondary)](https://www.igeeksblog.com/how-to-use-health-app-on-iphone/); older Apple guide using "Favorites" wording: [Apple iPhone User Guide, iOS 15](https://support.apple.com/guide/iphone/view-your-health-data-iphe3d379c32/15.0)
- iOS 27 redesign (current): new "Insights and Longevity tabs"; it was pulled from the iOS 27.2 beta and is back in the iOS 27.3 beta (expected December 2026); "requires an Apple Intelligence-capable iPhone." — [MacRumors, 2026-11-03](https://macrumors.com/2026/11/03/ios-27-3-health-app). Apple's own announcement: [Apple Newsroom, 2026-09](https://apple.com/newsroom/2026/09/apple-advances-health-and-fitness-capabilities-using-apple-intelligence/) (not fetched).

**Google / Samsung**
- Google Fit (2021, older): bottom bar Home, Journal, Browse, Profile; Browse lists six categories (Activity, Body measurements, Vitals, Nutrition, Sleep, Cycle tracking) and is also an entry point for adding data. — [9to5Google, 2021-07-29](https://9to5google.com/2021/07/29/google-fit-browse/)
- Google Health app 5.0 (Fitbit successor, 2026): reported four tabs Today, Fitness, Sleep, Health; one reviewer complained home/Health tiles are not movable. Secondhand via search summary; the TechRepublic page returned 403. — [TechRepublic](https://www.techrepublic.com/article/news-google-health-fitbit-app-ai-coach-widget/)
- Samsung Health redesign (rolling out from 2026-06-08): home highlights "five core pillars": Activity, Mindfulness, Nutrition, Sleep, Vitals; "new tabs at the top"; AI Energy Score. Customization not described. — [SamMobile, June 2026](https://www.sammobile.com/news/major-samsung-health-update-revamped-ui-new-ai-features/)

**Quantified-self**
- Exist (2025-08-20 redesign): Home tab with richer insights; "you can now pin four attributes to the top of your Home tab"; Review tab for faster manual entry; tapping an attribute shows "the full history of your raw data by month"; attributes/tags groupable into custom subgroups (new Symptoms, Medication groups). — [Exist blog: 2025 redesign](https://exist.io/blog/exist-2025-redesign)

**Self-hosted hubs**
- Home Assistant 2026.1: mobile Home dashboard puts summary cards (lights, climate, security, media, weather, energy) at top, "followed by your favorites and areas"; this "replaces the previous tab-based navigation" with "instant access ... without any extra taps"; on desktop "summaries displayed in the sidebar under the For you heading"; a Devices page lists devices not assigned to any area. — [HA 2026.1 release notes, 2026-01-07](https://www.home-assistant.io/blog/2026/01/07/release-20261/)
- HA organizes by Areas (devices inherit area; areas can auto-generate cards), Floors (group areas), Labels (cross-cutting, filter tables), Categories (per table). — [HA docs: Organizing](https://www.home-assistant.io/docs/organizing/)
- HA sidebar: users can reorder/hide sidebar items (profile setting or long-press on sidebar title), stored per user/browser; long-running requests for per-user/per-device default dashboards. — [HA community thread](https://community.home-assistant.io/t/manage-sidebar-menu-items-hide-add-move/219476); [frontend discussion #11278](https://github.com/home-assistant/frontend/discussions/11278); [Default dashboard per user/device? (2025–26)](https://community.home-assistant.io/t/default-dashboard-per-user-device/988518). 2026.10 reportedly groups default dashboard and sidebar order under a new Settings › Appearance section (search-result summary; not fetched) — [HA 2026.10 release notes](https://www.home-assistant.io/blog/2026/10/07/release-202610/)
- Nextcloud Hub 26 Spring (Nextcloud 34, mid-2026): the always-visible app bar was replaced by a top bar showing only the active app plus a dropdown/"waffle" switcher. Forum, 2026-07-07: "This is quite confusing for users who now don't know, where all the apps have gone" and "you now need always two mouse clicks to switch the app"; community reply: "the old menu is likely not to come back"; workaround is the Custom Menu app to pin apps; issue #59888 "App Navigation Redesign" asks to make it optional. — [Nextcloud forum: multiple apps visible in NC34](https://help.nextcloud.com/t/how-to-have-multiple-apps-visible-in-nextcloud-34/246656); [Nextcloud forum: Navigationsleiste nach Hub 26](https://help.nextcloud.com/t/navigationsleiste-wo-ist-sie-nach-update-nextcloud-hub-26-spring-34-0-0/245644); [Techzine on Hub 26 Spring](https://www.techzine.eu/news/collaboration/141976/nextcloud-hub-26-spring-is-designed-for-the-future/). Older admin-set default app order with per-user override: [Nextcloud forum](https://help.nextcloud.com/t/how-to-change-the-default-number-of-app-on-the-top-menu/24427/8)
- Immich (self-hosted photos): web left sidebar with Photos, Explore (faces grouped by person, places), Map, Sharing, Albums, Archive, Favorites, Trash. — [Olares Immich guide (secondary)](https://docs.olares.com/use-cases/immich.html); [Immich features](https://immich.app/features)

**Knowledge hubs / communication**
- Obsidian backlinks: "Linked mentions" (notes linking to the active note) and "Unlinked mentions" (notes mentioning its name); shown in a right-sidebar tab or "at the bottom of your note"; options to collapse, show more context, sort, filter. — [Obsidian Help: Backlinks](https://obsidian.md/help/plugins/backlinks)
- Slack 2023 redesign added a column of Home / DMs / Activity (and Files) next to the channel sidebar. — [Slack Help: overview of new design](https://slack.com/intl/en-au/help/articles/16764236868755-An-overview-of-Slacks-new-design). Critique (TidBITS, 2023-09-21): the new aggregated views "take it out of the necessary conversational context"; for single-workspace users a column with one icon is "wasting horizontal space"; redundant because users could already customize the channel sidebar. — [TidBITS](https://tidbits.com/?p=64071); backlash coverage: [VentureBeat](https://venturebeat.com/business/slack-lash-slack-defends-controversial-redesign-amid-sharp-criticism)

### Inferences
- Apple Health maps cleanly onto Life: Summary ≈ Diary "today", Browse ≈ the Life rail/index, category detail ≈ each app. Apps in this space keep primary nav to ~4–6 and push the rest into a Browse/index; Life's 9-item rail is fine on desktop but needs an index screen on phone.
- Home Assistant's 2026 move (summaries + favorites + areas on one Home, desktop summaries placed in the sidebar under "For you") is a precedent for showing small live summaries inside nav items (e.g., a badge or today's value next to a rail label) rather than a separate dashboard page.
- Nextcloud 34 is a fresh, directly relevant warning: replacing an always-visible list of apps with a switcher costs one click per switch and hides apps. Keep the Life rail visible on desktop.

### Gaps
- Gyroscope: only App Store listings/aggregators found (unified dashboard aggregating Apple Health, Fitbit, Oura, Garmin, etc.); no reliable description of its current navigation. — [App Store listing](https://apps.apple.com/app/apple-store/id1104085053)
- Microsoft account / Google Account dashboards and "super apps" (WeChat, Grab) were not researched in depth for lack of budget; no sourced findings to report.
- The claim that the iOS 27 Health app uses a combined search/browse button in the bottom bar came from an unidentified search summary; not verified, so not used.
- Immich's exact current web sidebar list is from third-party docs, not Immich's own documentation.

## Q3. Cross-app integration: entity pages, deep links, global search, related panels, shared date context, breadcrumbs

### Takeaway
Model Day, Person, Place (and Trip/Event) as first-class objects with one canonical home and one canonical URL each; every app shows its slice and links outward ("content is the navigation"). Carry the selected date/range as hub-level global state in the URL (the Kibana `_g` / Grafana "include time range" pattern), provide one Cmd+K palette across all apps, and add a backlinks-style "related" section on entity pages.

### Cited Findings
- Object-oriented UX (Prater, A List Apart, 2015-10-20, older but foundational): design objects (nouns) and their relationships before flows; "nest" objects inside each other to define cross-links; "The content is the navigation, and it's all in context"; OOUX "helps users get to content through content"; quoting Val Jencks, "The top navigation is the fire escape"; recipes↔chefs↔ingredients example avoids dead ends. — [A List Apart: Object-Oriented UX](https://alistapart.com/article/object-oriented-ux/)
- Kibana global vs app state: `_g` holds "Global UI state that should be shared and synced across multiple apps" (time range, refresh interval, pinned filters); `_a` is app-scoped; going Discover → Dashboard keeps the dashboard's state except the time filter, which follows the user. Kibana now advises using the target app's "locator" rather than hand-building another app's URL state. — [Kibana docs: Routing, Navigation and URL](https://www.elastic.co/docs/extend/kibana/kibana-navigation). The old implementation required a listener to rewrite "every single href in the navbar" on each global change. — [Kibana issue #39855](https://github.com/elastic/kibana/issues/39855)
- Grafana dashboard links: "Include current time range" means "the linked dashboard opens with the indicated time range already set"; "Include current template variable values"; for URL links both are enabled by default. — [Grafana docs: Manage dashboard links](https://grafana.com/docs/grafana/latest/dashboards/build-dashboards/manage-dashboard-links/)
- Command palette (Superhuman, 2021-10-12): "Wherever your user is in your app, they must be able to bring up the command palette by using the same keyboard shortcut" (Cmd+K); "You need fuzzy string matching" plus synonyms; "Show and hide commands based on what's currently active"; show each command's direct shortcut so users learn it; rank by usage/recency. — [Superhuman blog](https://blog.superhuman.com/how-to-build-a-remarkable-command-palette/). Blank palette should show recents/common actions; no-results state should offer a next step. — [SaaSUI (secondary)](https://www.saasui.design/blog/saas-search-command-palette-ux-patterns). Search results and executable commands should be modeled and presented differently. — [engineered.at (secondary)](https://engineered.at/articles/designing-command-palettes)
- Related/backlinks panels: Obsidian shows linked and unlinked mentions in a sidebar tab or inline at the bottom of the note. — [Obsidian Help: Backlinks](https://obsidian.md/help/plugins/backlinks)
- Breadcrumbs (NN/g, 2018-12-23, last reviewed 2026-09-01): show hierarchy, "not ... the history of pages traversed"; pick one canonical path for polyhierarchical pages; current page last and unlinked; they "augment but do not replace" global/local navigation; on mobile show only the last level or two. — [NN/g: Breadcrumbs](https://www.nngroup.com/articles/breadcrumbs/)
- Current location: many users arrive by deep link, so indicate location in the menu and breadcrumbs. — [NN/g: Menu-Design Checklist](https://www.nngroup.com/articles/menu-design/). On a detail page, highlight the owning type's nav item; "When opening a resource details page, don't add a new item to the side navigation." — [Cloudscape: Side navigation](https://cloudscape.design/patterns/general/service-navigation/side-navigation/)
- Nested nav selection should not change the outer context unexpectedly: for a sidebar inside a tab, "prevent selections in the sidebar from changing which tab is currently open." — [HIG Tab bars](https://developer.apple.com/design/human-interface-guidelines/tab-bars)
- Aggregation risk: Slack's aggregated Activity/DMs views were criticized for removing messages from their conversational context. — [TidBITS](https://tidbits.com/?p=64071)
- Entity grouping precedent: Home Assistant devices inherit their Area, and Areas auto-generate cards (a place-centric entity page). — [HA docs: Organizing](https://www.home-assistant.io/docs/organizing/)

### Inferences
- One canonical owner per entity type: Day → Diary, Person → People, Place → Location, Photo/Video → Media, Transaction → Finances, Card/ID → Wallet, Job/Project → Career. Other apps link to the canonical page rather than building their own copy; the rail highlights the owning app when an entity page is open (Cloudscape rule).
- URL scheme sketch (hash-based to fit a modal panel): `#life/diary/2026-11-06`, `#life/finances?date=2026-11-06`, `#life/location?from=2026-11-01&to=2026-11-07`, `#life/people/<id>`, `#life/location/place/<id>`. Treat `date`/`from`/`to` as global Life state (Kibana `_g`): switching apps keeps the date; date-agnostic apps (People, Wallet) ignore it but keep it in the URL so returning to a dated app restores it. Build cross-links through a single helper (Kibana "locator" lesson) instead of string-building in each app.
- Show the active date context visibly in the Life header (a date chip with prev/next day), and on dated views add "Same day in: Location · Media · Finances · Health" jump links. This makes the date context explicit rather than surprising.
- Entity pages as aggregations with exits: a Person page shows sections from each app (photos from Media, transactions, emails/events, places), each with "see all in <App>" deep links that open that app filtered to the person. Each aggregated item links back to its source context (Slack lesson).
- Breadcrumbs are optional with only two levels (NN/g: flat structures don't need them); a single-line title like "People › Ana" in the Life header plus the rail highlight is enough. Keep breadcrumbs hierarchical, not history; the browser back button handles history.
- One Cmd+K palette scoped to Life (or a "Life" filter in the host's palette) that searches entities across all 9 apps (people, places, days by date text like "march 3", transactions, photos) and includes navigation commands ("Go to Finances", "Open today"). Separate result groups by app and visually separate commands from records.

### Gaps
- Found no published case study of a multi-domain personal-data product that carries date context across sub-apps; the evidence comes from analytics tools (Kibana, Grafana), which are transferable but not consumer products.
- No user research found on how people use "related" panels in personal-data apps specifically.

## Q4. Home/overview: open on a dashboard or on the last app?

### Takeaway
For a daily-use tool, restoring the last place is the platform norm (Apple HIG), with a lightweight "today/summary" view as the default for first launch. Users praise small, user-pinned summaries (Apple Health Pinned, Exist's 4 pins, HA favorites) and reject "everything on one screen" consolidation (iOS 18 Photos, reversed in iOS 26).

### Cited Findings
- Apple HIG Launching: "Restore the previous state when your app restarts so people can continue where they left off"; "Avoid making people retrace steps ... scroll the view to people's most recent position, and display windows in the same state and location in which people left them." — [HIG Launching](https://developer.apple.com/design/human-interface-guidelines/launching)
- "Keep the side navigation open by default for returning users." — [Cloudscape: Side navigation](https://cloudscape.design/patterns/general/service-navigation/side-navigation/)
- iOS 18 Photos (2024): Apple's rationale — "As our features, users and libraries have grown, so has the density of the [Photos] app"; "Ultimately, we wanted to remove friction"; "automatic customisation is really key" — [9to5Mac, 2024-07-05](https://9to5mac.com/2024/07/05/ios-18-photos-app-redesign-interview/). Users called it hard to navigate, cluttered and overwhelming vs iOS 17; a "Customize & Reorder" option was the workaround; paid third-party apps sold the old UI — [BGR](https://bgr.com/tech/people-are-raging-over-the-ios-18-photos-app-redesign-heres-how-to-fix-it/); still divided two months later — [MacRumors, 2024-11-21](https://www.macrumors.com/2024/11/21/apples-photos-app-overhaul-controversial/); the carousel was dropped during beta after criticism (Gurman: "probably a little too bold and potentially confusing", via search summary) — [iMore](https://imore.com/apps/user-backlash-has-reportedly-caused-apple-to-rethink-ios-18s-photos-redesign)
- iOS 26 (WWDC, 2025-06-09): Federighi, "Many of you missed using tabs in the Photos app," and "Photos now features separate tabs for Library and for Collections." — [TechCrunch, 2025-06-09](https://techcrunch.com/2025/06/09/after-user-backlash-apple-brings-back-tabs-to-the-photos-app-in-ios-26/). Coverage also notes Collections sections can be collapsed/expanded (search summary) — [AppleInsider](https://appleinsider.com/articles/25/06/12/photos-in-ios-26-brings-back-tabs-and-generates-spatial-photos)
- Pinned summaries: Apple Health Summary with user-chosen Pinned metrics ([iGeeksBlog](https://www.igeeksblog.com/how-to-use-health-app-on-iphone/)); Exist "pin four attributes to the top of your Home tab" ([Exist, 2025-08-20](https://exist.io/blog/exist-2025-redesign)); Home Assistant Home = summaries, then favorites, then areas ([HA 2026.1](https://www.home-assistant.io/blog/2026/01/07/release-20261/)).
- Default-landing friction: HA users have asked for years to set the default dashboard per user/per device. — [HA frontend discussion #11278](https://github.com/home-assistant/frontend/discussions/11278); [HA forum, 2025–26](https://community.home-assistant.io/t/default-dashboard-per-user-device/988518)
- Customization is low-uptake: "most users are not interested in doing the work required to tweak the user interface"; personalization/customization "should enhance an already good experience, rather than try to fix a poor one." — [NN/g: Customization vs Personalization, 2016](https://www.nngroup.com/articles/customization-personalization/)

### Inferences
- Open Life on the last app and state (restore the hash: app, entity, date, scroll); first run or explicit "Today" → Diary at today. No separate tenth "Home" destination: Diary's today view is the overview (it already merges everything).
- If a summary strip is added to Diary/today, keep it short with sensible computed defaults plus optional pins (≤4–6, Exist/Health precedent), since few users customize (NN/g).
- Do not build a single mega-screen that tries to show all 9 apps at once (iOS 18 Photos lesson); keep the apps as separate destinations and make the overview link into them.
- Restoring state inside a modal means the Life window should own its URL fragment so reopening the panel, reloading, or sharing a link lands in the same place.

### Gaps
- No controlled study found comparing "restore last screen" vs "always open on home" for multi-app hubs; the guidance is platform convention plus product precedent.

## Q5. Two-level navigation pitfalls when the host app already has a sidebar

### Takeaway
Two persistent vertical navs cost width (lower content-to-chrome ratio) and blur "which level am I in". Mitigations: let the Life window cover or collapse the host sidebar, make the Life rail visibly scoped to Life, keep exactly one nav level inside Life (no third sidebar inside apps; use tabs or filters in content), and never hide the Life rail behind a switcher on desktop.

### Cited Findings
- Width cost: vertical nav "takes up more space" and lowers content-to-chrome ratio; example 5:1 with vertical menu vs 12:1 with horizontal bar at the same screen size. — [NN/g: Left-Side Vertical Navigation](https://www.nngroup.com/articles/vertical-nav/)
- Depth: "show no more than two levels of hierarchy in a sidebar"; beyond that use a split view (sidebar → content list → detail); consider auto-hiding the sidebar when the window shrinks. — [HIG Sidebars](https://developer.apple.com/design/human-interface-guidelines/sidebars). Avoid more than two tiers of cascading menus. — [NN/g: Menu-Design Checklist](https://www.nngroup.com/articles/menu-design/)
- Redundant extra column: Slack's added column was criticized as "wasting horizontal space" when it holds little, and as redundant with existing sidebar customization. — [TidBITS, 2023-09-21](https://tidbits.com/?p=64071)
- Hiding the second level costs clicks and discoverability: Nextcloud 34 users "don't know, where all the apps have gone" and need "two mouse clicks to switch the app." — [Nextcloud forum, 2026-07](https://help.nextcloud.com/t/how-to-have-multiple-apps-visible-in-nextcloud-34/246656)
- Secondary contextual panel pattern: a "second, contextual navigation panel ... that sits alongside the primary sidebar", noting that without a shared component each app re-implements "this panel-plus-drawer pattern" (mobile drawer stacking, back-button handling). — [Diamond Light Source sci-react-ui issue #274](https://github.com/DiamondLightSource/sci-react-ui/issues/274)
- Level cues: in nested sidebars both the open parent and active child should read as active. — [SaaSUI: sidebar patterns (secondary)](https://www.saasui.design/blog/saas-sidebar-navigation-ux-patterns). Visual cues between levels are often "too subtle for the eye to notice" (paywalled article, opening only). — [UX Movement](https://uxmovement.substack.com/p/a-better-approach-to-multi-level)
- Collapsing rules: collapsed rail with tooltip labels; "Don't use the collapsible navigation pattern with overly complex navigations." — [Cloudscape: Side navigation](https://cloudscape.design/patterns/general/service-navigation/side-navigation/)
- Modal caveat (NN/g, 2017, older): modals are for "short, direct dialogs"; multi-step or research-heavy work "warrants a full page"; modals "can cover important content and remove context." — [NN/g: Modal & Nonmodal Dialogs](https://www.nngroup.com/articles/modal-nonmodal-dialog/)

### Inferences
- Because Life hosts nine apps, it behaves like a workspace, not a dialog (NN/g modal guidance). Give it its own URL fragment, browser-back support, and a large size (near full-window on desktop, full-screen on phone). When the Life window is open, the host sidebar should be covered or auto-collapsed so only one vertical nav is visible at full width.
- If both navs must show at once (e.g., Life docked rather than modal), make the Life rail visually part of the Life window chrome (different surface color, inside the window border, Life title above it) so it does not read as a continuation of the host sidebar; consider the narrow labeled-rail form to save width.
- Keep inner apps free of their own left sidebars. Sub-navigation inside an app (e.g., Finances: Accounts / Transactions / Budgets; Media: Timeline / Albums / Map) should be tabs or segmented controls at the top of the content, or a list pane in a split view (Apple's "sidebar → list → detail" rule), giving at most host nav → Life rail → in-content tabs.
- Phone: the host sidebar is already a drawer; Life should not add a second drawer. Use the Life index screen (Q1) as the root and a stack with back navigation inside each app; centralize this responsive behavior in one Life shell component instead of per app (DLS lesson).

### Gaps
- No quantitative study found on nested/double sidebars; findings are design-system rules, product critiques, and forum feedback.
- Well-known two-column precedents (VS Code activity bar + side bar, Discord server rail + channel list, Microsoft Teams app bar) were not fetched, so they are not cited here.
